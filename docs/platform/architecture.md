# Целевая техническая архитектура

Статус: проект развития существующего React + NestJS + Prisma + PostgreSQL приложения. Разделы ниже **не означают, что новые модули уже реализованы**. Продуктовые правила — в [product.md](product.md), схема — в [domain.md](domain.md).

## Архитектурный выбор

Начинать с **модульного монолита**, одной транзакционной PostgreSQL и одного HTTP API. Календарь, участники, назначения и права сильно связаны; преждевременное разделение на микросервисы усложнит атомарность и контроль доступа. Границы модулей и событий оформляются так, чтобы позже можно было вынести тяжёлые уведомления, аналитику или файлы без смены предметной модели.

```text
React UI (admin / teacher / student)
    │ HTTP + проверяемые DTO, авторизованный доступ к файлам
    ▼
NestJS API: auth → workspace context → policy → use case → transaction
    ├─ catalog, people, courses, roster, calendar
    ├─ assignments, submissions, progress, materials
    ├─ notifications, audit, reporting
    └─ Prisma → PostgreSQL (источник истины)
                  └─ transactional outbox → worker → email/другие каналы
Файловое хранилище: защищённый локальный volume на одном узле;
объектное хранилище + независимые бэкапы перед несколькими узлами.
```

Клиентское приложение не является источником прав или расчётов. Сервер возвращает пагинированные списки, детали и отдельные сводки; UI может кешировать их по ключу пространства, курса, программы и фильтров. Изменение активного пространства/роли очищает этот кеш, чтобы данные не смешивались.

## Границы backend-модулей

| Модуль | Ответственность | Не должен владеть |
|---|---|---|
| Identity/Auth | Аккаунты, вход, сессии, приглашения, отзыв доступа, активный контекст. | Списком учеников в курсе. |
| Workspaces/Policy | Членство, назначения ролей, разрешения, единый механизм проверки области доступа. | Предметными оценками. |
| Catalog | Предметы, программы, версии, задания, правила расчёта и публикация. | Календарём конкретной школы. |
| Courses/Roster | Курсы, преподаватели, потоки, зачисления, вместимость и перевод. | Сданными файлами и оценками. |
| Calendar | Занятия, серии, состав, посещаемость, конфликты и замены. | Личными профилями как источником доступа. |
| Assignments | Работы, получатели, попытки, рецензии и персональные исключения. | Общим справочником заданий. |
| Progress | Неизменяемые события и пересчитываемые проекции по курсу/программе. | Первичными фактами сдачи. |
| Materials/Files | Метаданные, публикация, безопасная загрузка/скачивание и жизненный цикл бинарных объектов. | Самостоятельным решением, кому принадлежит курс. |
| Notifications | Адресные записи получателей и доставка по событиям. | Правами на исходный ресурс без повторной проверки при открытии ссылки. |
| Audit/Reporting | Журнал действий, операционные сводки и экспорт в допустимой области. | Изменением учебных фактов задним числом. |

Контроллеры тонкие: валидация входа, вызов use case, отображение результата. Use case устанавливает контекст `(actorUserId, workspaceId, capability)`, проверяет отношения, выполняет транзакцию и записывает доменное событие/аудит. Повторно используемые policy-функции проверяются отдельными тестами; непосредственный доступ к Prisma из произвольного контроллера исключается для защищённых сущностей.

## Область данных и авторизация

Токен подтверждает **личность и сессию**, но не является вечным снимком ролей. Роль и членство проверяются в БД/короткоживущем безопасном кеше для текущего пространства; отзыв или смена назначения вступают в силу без ожидания истечения JWT. Каждый запрос к данным содержит явный контекст пространства, а список ресурсов фильтруется на стороне БД до пагинации. Проверки «принадлежит ли актору этот курс/получатель/файл» применяются и к деталям, и к мутациям, и к потоковой выдаче файлов. Матрица — в [access.md](access.md).

Глобальный каталог и данные пространств хранятся раздельными логическими областями. Глобальная запись не должна содержать данные учеников. Локальные черновики/переопределения принадлежат конкретному пространству. На первом этапе изоляция выполняется обязательными FK, индексами, service policy и интеграционными тестами; PostgreSQL RLS можно добавить как защиту второго уровня после проверки всех системных заданий и миграций.

## Транзакции, конкуренция и идемпотентность

| Операция | Атомарная часть | Конкурентный риск и защита |
|---|---|---|
| Зачисление | Проверить курс/роль/вместимость, создать связь, обновить счётчик или проекцию, записать аудит/outbox. | Два запроса на последнее место: блокировка строки курса или сериализуемая транзакция с повтором; индекс не допускает дубль в курсе. |
| Создание/перенос урока | Проверить состав, интервалы и права, сохранить урок и участников, записать изменения. | Два параллельных урока: согласованная блокировка ресурсов преподавателей и учеников в детерминированном порядке плюс повтор при конфликте. Простая проверка `findFirst` недостаточна. |
| Публикация ДЗ | Зафиксировать ревизию задания и набор получателей, создать строки получателей, событие. | Повтор POST/сбой сети: `Idempotency-Key` и уникальность `(assignmentId,enrollmentId)`; число получателей в ответе. |
| Сдача/проверка | Сохранить попытку/рецензию, события прогресса и статус получателя, outbox. | Двойная проверка: ожидаемая версия записи (`If-Match`/revision) и конфликт `409`, без потери предыдущего отзыва. |
| Отмена/завершение курса | Зафиксировать решение по будущим урокам/работам и статус, аудит. | Массовое изменение выполняется пакетно с явным списком/предпросмотром; частичность и повторяемость определены до запуска. |

Блокировки не удерживаются на время отправки email или загрузки большого файла. Файл сначала принимается во временное хранилище с лимитом, проверяется и только после успешной транзакции становится опубликованной ссылкой; осиротевшие временные объекты убирает контролируемая уборка. Фоновые действия используют transactional outbox с уникальным ключом события, повторами и журналом ошибок. Потеря канала уведомлений не отменяет успешную учебную операцию.

## Календарь и повторения

Хранить UTC-моменты и исходный IANA timezone. Повторение задаётся локальным правилом и горизонтом материализации будущих занятий; исключение (перенос/отмена одного урока) — отдельная запись с привязкой к серии. При смене часового пояса или правила серии пересчитываются только ещё не проведённые события с предварительным просмотром. Проверка конфликтов включает со-ведущих, заменяющего преподавателя, всех приглашённых учеников и опционально аудиторию; интервал `[начало, конец)` позволяет соседние занятия без ложного конфликта. Групповое занятие создаётся/переносится как единая операция, а не N отдельных уроков.

## API и проекции чтения

Целевые эндпоинты описаны в [api-target.md](api-target.md). Списки принимают фильтры и стабильную сортировку, возвращают страницу и общее число или курсор там, где подсчёт дорог. У каждого детального ресурса один канонический ID и `revision/updatedAt`. Серверные сводки `today`, `toReview`, `overdue`, `capacity`, `conflicts` выполняются отдельными запросами/проекциями, а не из неполного `bootstrap`. Инвалидация кеша указывает конкретные коллекции и сводки; WebSocket не требуется для первого этапа, но контракты допускают обновление при внешних изменениях.

Справочник программ и их версий кешируется отдельно от личных данных и инвалидируется публикацией. Прогресс-проекция пересчитывается из событий. Если она временно отстала, UI показывает время актуальности; первичная история остаётся источником истины.

## Эксплуатация и масштабирование

На одном узле сохраняется текущий Docker Compose подход: PostgreSQL, backend, frontend и защищённый volume. Перед включением нескольких экземпляров backend потребуются общие лимиты авторизации/очередь, внешний или общий объектный storage, единые фоновые задания, координация расписания в БД, маршрутизация файлов и проверка отсутствия зависимости от памяти процесса. Не стоит считать горизонтальное масштабирование готовым только потому, что HTTP API не хранит сессию в памяти: текущие загрузки и rate limit имеют локальные компоненты.

Индексы проектируются под реальные запросы: `(workspaceId,status,createdAt)`, `(courseId,status)`, календарь по участнику/преподавателю и времени, получатели по ученику/статусу/сроку, история по зачислению/времени. Для больших списков использовать cursor pagination с уникальным tie-breaker; `offset` допустим на небольших административных наборах. Запросы на видимость материалов не должны сканировать все уроки и ДЗ ученика; доступ определяется явными связями публикации.

Бэкап включает БД и файловые объекты как согласованную пару, проверку контрольных сумм и восстановление в изолированной среде. Плановое расписание и внешняя копия активируются на реальном сервере отдельно; наличие скрипта в репозитории не означает работающий бэкап. Миграции используют expand/backfill/switch/contract, проверку на копии, метрики ошибок и подготовленный rollback; подробности — в [migration-and-acceptance.md](migration-and-acceptance.md).

Наблюдаемость: структурированные логи с `requestId`, события аудита, ошибки фоновых задач, длительность и число конфликтов календаря, время публикации ДЗ, задержка уведомлений и проекции прогресса, объём хранилища, результат/давность бэкапа. Содержимое работ, пароли, токены и персональные заметки в диагностические логи не попадают.

## Архитектурные запреты первого этапа

- Не хранить роли, доступ и состав курса только в JWT или React state.
- Не вычислять права на файл по совпадению номера задания, имени файла или предсказуемому URL.
- Не создавать отдельную несовместимую модель `GroupLesson` рядом с `IndividualLesson`.
- Не обновлять опубликованные критерии версии программы задним числом.
- Не удалять каскадом учебную историю при завершении зачисления или архивировании курса.
- Не отправлять внешние уведомления внутри открытой транзакции БД.
