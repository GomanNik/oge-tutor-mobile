# Блок 1: проверка и границы готовности

Дата проверки: 2026-10-22. Среда: Windows, Docker Desktop, PostgreSQL 16-alpine, изолированные БД блока 1. Все адреса и аккаунты ниже относятся к локальной разработке. Этот отчёт не разрешает промышленный rollout или merge PR.

## Подтверждено

| Область | Результат |
|---|---|
| Сборка и unit | `pnpm run quality`: backend build/lint, 64 unit-теста, frontend build/lint/typecheck, 29 UI/unit-тестов — успешно. Production frontend build выполнен с `VITE_API_BASE_URL=http://127.0.0.1:3001`. |
| HTTP и PostgreSQL | `pnpm run backend:test:e2e` на отдельной мигрированной PostgreSQL: 7 сценариев — успешно. Проверены v1 учебный поток, v2 администрирование, разделение двух пространств, ревизии, приглашения и повторная доставка, ограничения частоты, конкурентная защита последнего администратора, закрытие v1 при приостановке с сохранением доступа в другое v2-пространство. |
| Миграции | Пустая БД: `migrate deploy`, одноразовый bootstrap, повторный bootstrap без дублирования. Копия старой схемы: 2 преподавателя, 2 ученика (один отключён), 1 урок и 1 сессия; после миграции — 2 mapping, 2 пространства, 4 membership, 6 grants. Повторный CLI backfill добавил 0 строк. `prisma migrate status`: 7 миграций, схема актуальна. |
| Backup/restore | `pg_dump -Fc` и `pg_restore --exit-on-error` изолированной legacy-фикстуры в новую БД. Сравнение до/после: `User=4`, `TeacherProfile=2`, `StudentProfile=2`, `Lesson=1`, `AuthSession=1`, mapping=2, membership=4 и контрольная сумма `id+passwordHash` совпали. Это не restore данных будущего VPS. |
| Контейнеры | `docker compose config` и сборка backend/frontend образов — успешно. Существующие контейнеры пользователя на других портах не заменялись. |
| Ручной UI | На локальном API и SMTP Mailpit: вход администратора, список/управление участниками, приглашение через настоящее письмо, открытие ссылки, принятие новым аккаунтом, вход и проверка student-контекста, видимость нового участника администратором. Токен удаляется из URL после открытия. |
| Размер списков | 10 000 участников и 100 000 событий аудита; первая/средняя/последняя страницы проверены с `EXPLAIN (ANALYZE, BUFFERS)`. Подробности в [замерах](block-1-performance.md). |

## До разрешения merge

- Перенести локальные проверки пустой и старой БД в воспроизводимые CI migration-тесты; отдельно проверить частично прерванный backfill и ограничения FK/partial index (B1-M01–M04).
- Довести автоматические проверки до полной матрицы B1-P01/I04/I06/I07/C01: чужой ID для каждого маршрута, одновременное принятие одного приглашения, имитация остановки процесса после commit, приглашение уже активного и приостановленного участника, проверка ответов по опубликованной OpenAPI-схеме. Текущий E2E проверяет основные потоки, но не всю таблицу случаев.
- Провести и приложить повторяемую проверку клавиатуры и мобильного viewport, включая отсутствие горизонтального переполнения (B1-F03); ручной локальный проход не заменяет этот артефакт.
- Подключить производственные метрики отказов входа/прав и состояния outbox (B1-N02). Сейчас безопасные структурированные HTTP/operation-логи и SQL-контроль backlog доступны, но отдельный сборщик/экспорт метрик не настроен.
- Дождаться CI созданного PR и независимой проверки diff. До этого PR должен оставаться черновиком.

Из-за отсутствия VPS настройка расписания backup и восстановление реальной БД отдельно ожидают инфраструктуру. Порядок rollout и rollback описан в [операционной инструкции](block-1-operations.md).
