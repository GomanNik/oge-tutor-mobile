# Блок 1: локальная проверка страниц

Дата: 2026-10-22. Среда: PostgreSQL 16-alpine в Docker Desktop на Windows, отдельная временная БД. Это проверка плана и корректности курсора, не обещание времени ответа на VPS.

В одном пространстве сгенерированы 10 000 участников и 100 000 событий аудита. Для всех трёх v2-списков (`members`, `invitations`, `audit-events`) первый запрос получает максимум `limit + 1` ID параметризованным SQL, затем один Prisma-запрос загружает только эти записи/связи. Число SQL-запросов на страницу постоянно и не зависит от размера пространства. Курсор привязан к пространству и фильтрам; смена области/фильтра даёт `400`.

Для участников используется индекс `(workspaceId, createdAt, id)`, для аудита `(workspaceId, occurredAt, id)`. Сравнение `(createdAt,id) > (:time,:id)` или `(occurredAt,id) < (:time,:id)` помещается в `Index Cond`. До изменения форма `createdAt > :time OR (createdAt = :time AND id > :id)` на последней странице участников показывала `Rows Removed by Filter: 9975`, 233 буфера и около 3.5 мс только для ID. После изменения индекс выполняет позиционный поиск.

| Набор/страница | План | Буферы | `Execution Time` |
|---|---|---:|---:|
| Участники, первая | Index Only Scan | 3 | 0.305 мс |
| Участники, средняя | Index Only Scan | 6 | 0.184 мс |
| Участники, последняя | Index Only Scan | 6 | 0.145 мс |
| Аудит, первая | Index Only Scan Backward | 5 | 0.059 мс |
| Аудит, средняя | Index Only Scan Backward | 8 | 0.121 мс |
| Аудит, последняя | Index Only Scan Backward | 8 | 0.136 мс |

Проверка использовала `EXPLAIN (ANALYZE, BUFFERS)` после `ANALYZE` таблиц. Время относится к выборке ID, не включает вторую загрузку связей, HTTP, сериализацию и сеть. Фильтр подстроки по имени/email (`ILIKE`) пока не имеет отдельного trigram-индекса; при большом числе участников или частом поиске этот фильтр нужно измерить на реальных данных и при необходимости добавить индекс отдельной миграцией. Числа локальной машины не являются SLA.
