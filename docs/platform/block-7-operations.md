# Блок 7: переключение, проверка и восстановление

Это runbook, не команда на изменение рабочей системы. Выполняет ответственный оператор с доступом к конфигурации, БД, хранилищу и журналу развёртывания. У владельца проекта VPS пока нет; таймер бэкапов, реальный SMTP и production-переключение не объявляются выполненными. Автоматические испытания используют только disposable-базы и фиктивные аккаунты.

## Предохранители

- Не запускать `prisma migrate reset`, demo/browser seed или E2E на рабочей БД.
- Обновление схемы: только `prisma migrate deploy` после проверки копии и backup. Не редактировать применённые миграции.
- `LEGACY_API_MODE=disabled` открывает запись перенесённых ресурсов через v2 и фиксирует барьер в БД. Это не безобидная настройка отображения.
- Не удалять `LegacyCutover`, старые таблицы, колонки, файлы или триггеры для «починки запуска».
- Команды принятия checksum и замены приглашений изменяют данные, требуют `--confirm apply` и содержательную причину. Проверка сама ничего не исправляет.
- Отчёты могут содержать внутренние ID; хранить их как эксплуатационные данные с ограниченным доступом, не публиковать в репозитории. Токены, пароли, dump и содержимое файлов не помещать в PR.

## Конфигурация

| Переменная | Значение и смысл |
|---|---|
| `LEGACY_API_MODE` | enabled по умолчанию, затем read_only, затем disabled. Один режим на все экземпляры backend. |
| `LEGACY_CUTOVER_CONFIRM` | Для disabled точное значение `verified-backup-and-reconciliation`. Не является автоматической проверкой backup, а явным подтверждением оператора. |
| `LESSON_SERIES_WORKER_ENABLED` | `false` выключает продление серий; по умолчанию таймер включён вне test/CLI. |
| `LEARNING_NOTIFICATIONS_WORKER_ENABLED` | `false` выключает внешнюю доставку учебных уведомлений. Внутренние адресные записи продолжают создаваться транзакционно. |
| `WORKSPACE_INVITATIONS_WORKER_ENABLED` | `false` выключает обработку почтовых приглашений. |
| `UPLOAD_DIR` | Реальный корень файлов, доступный процессу. При восстановлении пути БД и mount должны согласовываться. |
| `CLI_MODE` | Внутренний предохранитель одноразовых операторских команд: не запускаются периодические таймеры. Не задавать true штатному HTTP backend. |

Нельзя одновременно держать старый backend, который пишет v1, и новый backend в disabled: код старой версии не знает барьер. Нужна остановка всех писателей, согласованная конфигурация и одно окно переключения, а не rolling update несовместимых режимов. Применить настройку ко всем процессам/репликам и проверить их health/runtime по отдельности.

## Этап A: подготовка без отключения

1. Принять PR и проверить CI объединённого main. Зафиксировать SHA, версии образов, состав миграций и конфигурацию без секретов.
2. Инвентаризировать все клиенты v1, внешние интеграции, роли/аккаунты, объёмы БД/файлов, реальные абсолютные пути, ожидаемое окно простоя и ответственного за решение continue/abort.
3. Сделать согласованный backup БД **и файлов** по [backups.md](../backups.md), проверить manifests и восстановить его на изолированной копии. При записи файлов во время копирования нужна остановка писателей либо согласованный snapshot; последовательный live-copy не гарантирует консистентность.
4. На восстановленной копии выполнить migrate deploy; проверить паритет, права и полный пользовательский путь. Убедиться, что все используемые старые файлы действительно присутствуют.
5. Развернуть совместимый Block 7 с mode enabled. Проверить `/health/ready`, v2 runtime, входы трёх ролей и доступ к историческим данным. Импортированные сущности пока остаются read-only в v2.
6. Подтвердить рабочую доставку v2-приглашений и восстановления пароля через SMTP на реальной тестовой почте. Noop доказывает подготовку ссылки, не доставку письма.
7. Объявить период read_only и короткое окно полного запрета записи на финальную сверку. Включить наблюдение за legacy requests и очередями.

## Этап B: остановка v1-записи и сверка

1. Перевести все актуальные экземпляры в `LEGACY_API_MODE=read_only`, перезапустить. Учебные POST/PATCH/DELETE v1 должны возвращать `403 legacy_api_read_only`; старое чтение пока доступно, восстановление/выход разрешены. Убедиться, что не осталось старых писателей/worker/CLI.
2. Подготовить замещающие v2-приглашения всем получателям ещё действующих legacy invite. Это можно сделать существующим административным UI/API. Проверить правильные пространство, email и роль student; повторный вход существующего пользователя не должен требовать нового аккаунта.
3. При необходимости осознанно погасить старые приглашения командой ниже. Команда откажется, пока хотя бы одному адресу нет pending v2-приглашения student с неистёкшим сроком. Она не отправляет письма и не меняет учебную историю.
4. Выполнить release verify для каждого пространства/всех пространств. Проверка имеет код выхода **0** только при согласованных данных, режиме не enabled, доступных файлах с совпавшими checksum и отсутствии несопоставленных legacy-преподавателей. Код **2** означает незавершённые критерии, **1** ошибку выполнения. Сохранить отчёт в новый путь.
5. Файлы без checksum не объявлять исправными. Сравнить их с доверенным backup/инвентаризацией. Только после этого принять исходный manifest отдельной командой. До 5000 таких файлов на пространство за одну baseline-операцию; превышение блокирует принятие, а не даёт усечённый успех. Файл с известным несовпадающим hash сначала расследовать и восстановить из доверенной копии.
6. Устранить несогласованности/очереди, пересобрать проекции штатным `learning:operator rebuild-progress` при необходимости, повторить verify. Не подменять сверку UPDATE счётчиков.
7. На время финального backup/проверки остановить и v2-запись, а также внешнюю обработку очередей. HTTP сверка является snapshot, не долгоживущей блокировкой. Повторно проверить весь инвентарь после последней записи.

Примеры из корня проекта с уже настроенными DATABASE_URL, UPLOAD_DIR и прочими переменными среды. ID/причина и пути ниже заменяются оператором; не подставлять секреты в историю команд:

```powershell
$env:LEGACY_API_MODE = 'read_only'
pnpm --dir oge-tutor-backend run release:operator verify --output release-before-cutover.json
pnpm --dir oge-tutor-backend run release:operator verify --workspace WORKSPACE_ID
pnpm --dir oge-tutor-backend run release:operator retire-legacy-invites --workspace WORKSPACE_ID --reason 'Замещающие приглашения v2 проверены оператором' --confirm apply
pnpm --dir oge-tutor-backend run release:operator adopt-file-checksums --workspace WORKSPACE_ID --reason 'Байты сверены с доверенным контрольным backup' --confirm apply
```

`--output` использует создание нового файла `wx`, не перезаписывает прошлое доказательство. CLI проверяет файловые страницы по 100 и пространства по 25; конечный JSON-отчёт аккумулирует результаты всех выбранных пространств. Для большого инвентаря ограничивать проверку одним пространством и сохранять отдельные отчёты. Hash-файлы не вычисляются в HTTP запросе административной страницы.

## Этап C: единственный источник записи v2

1. С остановленными писателями создать финальный согласованный restore point и сохранить результаты проверки восстановления. Зафиксировать точку отсечения и принявшего решение человека.
2. Задать disabled и ACK, запустить новый backend. Guard при старте создаст `LegacyCutover('v2-authoritative')`. Если marker уже есть, запуск enabled/read_only завершится ошибкой, без HTTP ready.
3. Проверить публичный `/api/v2/runtime`: `legacyApiMode=disabled`, `legacyDataRetained=true`. Проверить старые `/auth/login`, `/bootstrap`, `/lessons`, `/homeworks`, `/files/:id/download`: `410 legacy_api_disabled`. Предусмотрены Deprecation/Link headers. v2 и health не блокируются.
4. Переключить все клиенты на v2, снять запрет записи. У перенесённых ресурсов `legacy=true`, `legacyReadOnly=false`. Не удалять marker после старта, даже если ещё не заметны новые записи.
5. Выполнить smoke: admin видит свои роли/сверку; teacher меняет будущий перенесённый урок и создаёт новую серию; student видит только своё, скачивает разрешённый материал и сдаёт открытую перенесённую работу; teacher публикует проверку, student видит результат. Проверить восстановление и смену пароля с отзывом старых сессий.
6. Повторить release verify; сравнить counts и конкретные исторические записи, а не требовать равенства живой v2-записи старому зеркалу. Старые исходники и файлы остаются для расследования.
7. Включить нужные worker на фактическом сервере, проверить due/failed, доставку и корректность нового горизонта. Не запускать в production browser/demo seed и test:restore.

```powershell
$env:LEGACY_API_MODE = 'disabled'
$env:LEGACY_CUTOVER_CONFIRM = 'verified-backup-and-reconciliation'
pnpm --dir oge-tutor-backend exec prisma migrate deploy
pnpm --dir oge-tutor-backend run build
pnpm --dir oge-tutor-backend start
```

Для Docker переменные заданы в compose; существующие контейнеры не получают env без пересоздания. Пользовательские секреты и volume сохраняются. Пересоздание выполняется оператором только после принятия релиза и проверенного backup, а не автоматически при merge.

## Серии: штатная эксплуатация

В UI: Расписание → Серии → выбрать курс → правило/состав → предпросмотр → подтверждение. Причина обязательна для изменения/паузы/возобновления/отмены. Preview устарел: обновить серию, проверить новый список и подтвердить заново; не повторять старый запрос с новым ключом вслепую.

Пауза оставляет созданные занятия. Если нужно убрать будущее расписание, выбрать отмену серии и проверить полный список отмен. Отмена терминальна. Для переноса одного занятия редактировать экземпляр в календаре с причиной, не менять правило всего курса.

Разовый обход due-серий:

```powershell
pnpm --dir oge-tutor-backend run series:operator materialize
```

Результат `{handled, created}` отражает только этот проход (максимум 50), не размер всего архива. Просроченное право/зачисление, конфликт или DST нельзя «обойти» этой командой. Устранить причину и подтвердить resume через preview. Терминальное completed/canceled не возобновляется. Для горизонта далеко за текущими 7–90 днями отсутствие уроков ожидаемо.

## Мониторинг и реакция

Метрики защищены прежним токеном `/internal/metrics`: `oge_legacy_requests_total{mode=...}`, `oge_legacy_last_request_unixtime`, `oge_lesson_series_due`, `oge_lesson_series_failed` плюс существующие очереди/ошибки/backup-метрики. Метки ограничены конечными режимами, без email/ID ресурса/сырого пути.

- Due не уменьшается несколько проходов: проверить worker flag, здоровье БД, права последнего оператора, ошибки/nextRunAt и лимит партии.
- `failures>0`: открыть серию, исправить причину, повторить preview; после 5 неудач будет paused. Не обнулять failures SQL-запросом вместо исправления.
- Растут legacy requests после cutover: найти и обновить потребителя по журналу/инвентарю, не включать v1 обратно.
- Ошибка SHA/размера/недоступный файл: остановить необратимые действия, проверить root/mount/права и доверенный backup. Не принимать новый checksum повреждённого файла.
- Несогласованная проекция: исследовать immutable-события, выполнить rebuild, повторить сверку. Не удалять историю.

Численные пороги alert/SLO согласуются после замера на фактической инфраструктуре. Локальный тест не подтверждает производительность нескольких тысяч курсов.

## Восстановление

Автоматический безопасно ограниченный drill для CI/локальной disposable-среды:

```powershell
$env:RELEASE_POSTGRES_CONTAINER = 'NAME_OF_TEST_POSTGRES_CONTAINER'
$env:RELEASE_DRILL_REPORT = 'test-results/release-restore-drill.json'
pnpm --dir oge-tutor-backend run test:restore
```

Нужны Docker, собранный backend, актуальный Prisma client и DATABASE_URL, явно обозначающий test/e2e/ci. Скрипт создаёт собственные БД `oge_restore_ci_<hex>_source/restored`, собственную папку, файлы и случайный свободный HTTP-порт; не очищает базу из DATABASE_URL и не использует рабочие файлы. Генерирует native-фикстуру, dump, manifests, намеренно повреждает только копию собственного файла, проверяет отказ, восстанавливает БД+файлы и запускает HTTP проверки. Нужные только фикстуре абсолютные storagePath заменяются на её восстановленный temp-root; это не автоматическое исправление production путей. Cleanup ограничен сгенерированными именами/папкой и своим дочерним процессом.

Проверяется: две файловые SHA, отвергнутая повреждённая копия, вход восстановленных teacher/student, защищённые скачивания материала и приватного ответа, чтение старой попытки, новая публикация/сдача/проверка/прогресс, disabled v1. `fixtureOnly=true` в отчёте явно запрещает выдавать drill за восстановление пользовательского backup. На сервере отдельно повторяется restore фактического архива, с его путями, ключами, SMTP и реальными объёмами.

## Откат и физическое сужение

До disabled и новых authoritative-записей допускается возврат совместимого кода согласно исходному плану миграции. После marker предпочтителен forward fix на сохранённой расширенной схеме. Откат старого кода/смена env после новых записей теряет их смысл и обходом marker не лечится.

Если выбран полный restore: остановить все писатели и доставку, экспортировать доступные записи после restore point для разбирательства/компенсации, восстановить согласованную БД вместе с файлами и конфигурацией на отдельной среде, проверить доступ/сценарии/инвентарь, получить осознанное согласие на потерю/повторный ввод данных после отсечения, затем переключить трафик. Не выполнять migrate down и не удалять таблицы наугад. Снимок после marker по-прежнему authoritative v2.

**ADR-007: отложенное сужение.** Альтернативы: сразу DROP v1; бессрочная двойная запись; отключение v1 с сохранением схемы. Выбрано третье: доступ к перенесённой истории нужен сейчас, а перечень внешних потребителей и период наблюдения пока не подтверждены. Поэтому Block 7 завершает функциональное переключение, но не уничтожает источник и совместимые триггеры. Следующий отдельный maintenance PR должен получить разрешение владельца, срок наблюдения, нулевой инвентарь потребителей, полный граф FK/триггеров/экспортов и повторный restore/паритет; только после этого допустим физический contract. Это не скрытый восьмой продуктовый блок.
