# Блок 2: предметный каталог и версии экзаменов

Статус: реализация в отдельной ветке `codex/block-2-catalog`; не является разрешением на развёртывание. Этот блок расширяет приложение без переключения старого учебного кабинета. Курсы, группы, зачисления и новый прогресс относятся к следующим блокам.

## Граница блока

В блок входят предметы, программы ОГЭ/ЕГЭ, варианты (например, ЕГЭ/математика/база и профиль), версии по периодам и ревизиям, определения заданий, метаданные правила оценки, явные сопоставления заданий двух опубликованных версий, локальное и глобальное владение, управление в UI, типизированный HTTP API и импорт текущего каталога 1–25. В блок **не** входят выполнение формулы оценивания, прогноз для новых программ, назначение программы ученику, привязка старых уроков/работ к курсу, массовый импорт официальных экзаменационных спецификаций и перенос исторического прогресса. Число заданий, их коды и максимумы не зашиты в v2.

## Модель и ограничения

| Сущность | Смысл |
|---|---|
| `CatalogGrant` | Независимое от ролей пространства право управления **глобальным** каталогом. Выдаётся только оператором БД, не администратором пространства через API. Проверяется по БД при каждом изменении. |
| `Subject` | Код уникален в области (`global` или `w:<workspaceId>`), название и состояние `active/archived`. Архивирование не удаляет программы. |
| `ExamProgram` | Экзамен (`oge/ege`), предмет, вариант и уникальный в области код. Уникальна комбинация области, экзамена, предмета и варианта. Глобальная программа использует только глобальный предмет; локальная может использовать свой или глобальный. |
| `ProgramVersion` | `(programId, period, revisionNumber)` уникальна. `draft → published → archived`; `revision` защищает конкурентные изменения, `publishedAt` сохраняется. После публикации содержимое не редактируется. |
| `TaskDefinition` | Собственный ID, строковый код, порядок, название, темы, тип, максимальный балл, структурированные критерии. Код и порядок уникальны **внутри версии**; одинаковый номер в другой версии ничего не доказывает. |
| `ScoringRule` | Метаданные ссылки на `historical_heuristic` или `verified_reference`, код, описание и источник. Здесь **нет исполняемого алгоритма** и v2 не строит прогноз. Подтверждённый источник обязателен для `verified_reference`. |
| `TaskMapping` | Только явная связь двух заданий опубликованных/архивных версий **одной программы**, с основанием и создателем. Ошибочная связь отзывается с причиной и автором; история не удаляется. Перенос аналитики по равному коду без действующей связи запрещён. |
| `CatalogAuditEvent` | Автор или оператор, действие, область, цель, безопасный состав изменений, `requestId`, время. Создание, правки, публикация, архивирование и выдача глобального права отражаются в журнале. |

Внешние ключи сохраняют версии и задания от каскадного удаления. Условия `scopeKey`, позиции и максимального балла проверяются БД. Триггеры запрещают изменение заданий и правила оценки после публикации, а также исправление содержимого опубликованной версии даже при прямой SQL-команде. Дополнительные проверки области и полноты публикации выполняются в сервисе. Критерии, если заданы, имеют уникальные коды и сумму баллов, равную максимуму задания. Публикация требует источник HTTPS, минимум одно задание и максимумы всех заданий; правило оценки при этом может отсутствовать.

## Доступ

- Аутентифицированный пользователь читает глобальные опубликованные и архивные версии. Для локального каталога нужно активное членство в том пространстве и `X-Active-Role` с действующим назначением; чужой ID возвращает 404.
- Локальный администратор создаёт и изменяет только записи своего пространства. Администратор A не получает право на локальный каталог B или общий каталог.
- Глобальный редактор с `CatalogGrant` управляет только общими записями. Его право не открывает частные каталоги пространств.
- Черновики версии читает только управляющий владелец. Преподаватель и ученик видят опубликованные/архивные версии своего пространства и общего каталога.
- Назначение/отзыв членства или глобального права вступает в силу при следующем запросе, не ждёт истечения JWT.

## HTTP-контракт

Все маршруты ниже имеют префикс `/api/v2` и требуют Bearer JWT. Для локальной области списки принимают `workspaceId`, а запросы — `X-Active-Role`. Без `workspaceId` списки читают только глобальные записи. Прямые детали локального объекта также требуют роль. Списки возвращают `{items,total,page,pageSize}` (страница 1..100000, размер 1..100), детали `{item}`, изменения `{item,changed,requestId}`; изменения задания и правила дополнительно возвращают `versionRevision`.

| Маршрут | Назначение |
|---|---|
| `GET/POST /subjects`, `GET/PATCH /subjects/:id`, `POST /subjects/:id/archive` | Список, создание, деталь, переименование, архивирование предмета. Фильтры `q/status`. |
| `GET/POST /programs`, `GET/PATCH /programs/:id`, `POST /programs/:id/archive` | Программы; фильтры `q/status/subjectId/examType/variant`. |
| `GET/POST /programs/:id/versions` | Версии программы; фильтры `period/versionStatus`. Создание всегда черновое. |
| `GET/PATCH /program-versions/:id`, `POST /program-versions/:id/publish`, `POST /program-versions/:id/archive` | Деталь, изменение источника/примечания черновика, публикация и архивирование. |
| `GET/POST /program-versions/:id/tasks`, `PATCH/DELETE /program-versions/:id/tasks/:taskId` | Страница заданий и изменение только черновика. |
| `POST /program-versions/:id/scoring-rule` | Установить/заменить метаданные правила только у черновика. Не включает прогноз. |
| `GET/POST /task-mappings`, `POST /task-mappings/:id/revoke` | Явные связи; чтение требует `fromVersionId` и `toVersionId`. По умолчанию только действующие связи; управляющий может запросить `includeRevoked=true`. Отзыв требует причину и `If-Match` ревизию связи. |

`Idempotency-Key` обязателен для создания предмета, программы, версии и связи заданий. Повтор с тем же телом возвращает прежний результат; другое тело даёт 409. `If-Match` с числовой `revision` обязателен для изменения/архивирования/публикации; для заданий и правила используется ревизия **версии**, возвращаемая после мутации. Отсутствие заголовка — 428, устаревшая ревизия — 412, недопустимое состояние — 409, предметная валидация — 422. Все ответы и ошибки отражены в Swagger `/api/docs`.

## Импорт существующего кабинета

Миграция создаёт общие `math`, `oge-math`, версию периода `legacy-import`, 25 определений с теми же кодами и названиями, что в прежнем UI, и `ScoringRule.kind=historical_heuristic`. ID фиксированы и пригодны для блока 3. Версия опубликована **только для сохранения существующей семантики**, а не как утверждение официальной спецификации экзамена. `maxScore` и критерии у этих заданий не выдуманы: баллы остаются `null`, а прежняя формула живёт только в v1 до отдельной миграции прогресса. Эта историческая исключительная запись создаётся SQL-миграцией до установки триггера неизменяемости; обычный API не позволяет публиковать новую версию с неизвестными максимумами.

Миграция расширяет схему и не удаляет прежние колонки. Старые маршруты и учебные данные работают независимо. Проверка перед выпуском: 25 legacy-заданий, одна legacy-версия, отсутствие новых FK к старым урокам/работам и равенство контрольных чисел исторических записей до/после.

## Операторское право

Для существующего аккаунта оператор с доступом к БД задаёт `DATABASE_URL` и `CATALOG_USER_EMAIL` в окружении, затем выполняет:

```powershell
pnpm --dir oge-tutor-backend run catalog:operator -- grant
pnpm --dir oge-tutor-backend run catalog:operator -- revoke
```

Команда идемпотентна, пишет событие с `actorKind=operator` и выводит только ID и `changed`. Email не передаётся аргументом командной строки и не печатается в журнал. Не давайте `DATABASE_URL`/пароли в чат, коммит или публичный CI-лог. До grant подтвердите личность владельца аккаунта через утверждённый административный процесс. У `GET /api/v2/me` и ответа входа поле `catalogManage` указывает текущее право для интерфейса, но backend его перепроверяет.

## Приёмка и выпуск

- Пустая PostgreSQL: `prisma migrate deploy`, `prisma migrate diff` без дрейфа, legacy 25 записей, повторный `migrate deploy` без дублей.
- Backend: сборка, линтер, unit; HTTP e2e на PostgreSQL для двух пространств, глобального права, запрета чужих ID, нескольких типов экзамена/вариантов, идемпотентности, ревизий, публикации, запрета SQL-правки, новой ревизии и явного mapping.
- Frontend: сборка, линтер, typecheck, тесты создания/чтения, read-only роли, очистки предыдущего списка при переключении и глобального редактора без пространства; ручной проход на узком и широком viewport.
- Полный `pnpm run quality`, `pnpm run audit`, Docker build обоих образов и CI на коммите ветки. Наличие зелёных тестов не заменяет независимую проверку PR.
- Перед реальным развёртыванием: backup/restore БД и файлов, сверка количества данных и времени простоя, план возврата к совместимому коду. VPS пока нет, поэтому производственный rollout и расписание бэкапов не подтверждены.

## Следующий блок

Блок 3 создаёт курсы, преподавателей и зачисления по конкретной **опубликованной версии**. Он сохранит отдельный прогресс каждого зачисления и перенесёт старую пару преподаватель–ученик в индивидуальный курс с явной сверкой ID. Группы и расписание затем используют ту же программу и ту же модель участника, а не отдельный «групповой каталог».
