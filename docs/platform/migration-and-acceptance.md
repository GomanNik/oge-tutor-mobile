# Переход, проверки и критерии приёмки

Статус: план, **не выполненная миграция**. Никакая команда из этого документа не применяется к работающей БД автоматически. Новая модель — в [domain.md](domain.md), сценарии — в [workflows.md](workflows.md), права — в [access.md](access.md).

## Условия начала

До изменения схемы принять открытые решения [индекса](README.md), инвентаризировать реальные данные/файлы/аккаунты, замерить объём и частоту запросов, определить владельца каталога и политику персональных данных. На тестовой копии проверить корректность текущих миграций, состав бэкапа и восстановление БД **вместе с файлами**. Выбрать окно переключения и ответственного за решение «продолжить/откатить». До появления VPS активация серверного расписания бэкапов остаётся отдельной незавершённой операционной задачей.

## Последовательность реализации

| Этап | Изменение | Выходной критерий |
|---|---|---|
| 0. Базовый замер | Зафиксировать текущие ответы/API, тестовые сценарии, количество пользователей, уроков, ДЗ, файлов; подготовить копию данных без раскрытия лишних персональных сведений. | Существующие тесты зелёные, есть проверенный restore и карта текущих FK/каскадов. |
| 1. Расширение схемы | Добавить пространства/членство, каталог/версии, курсы, преподавателей, зачисления, участников урока, получателей ДЗ и аудируемые состояния, не удаляя старые колонки. | Миграция `deploy` работает на пустой и копии существующей БД; старый код продолжает работать. |
| 2. Перенос данных | Создать одно пространство, импортировать версию ОГЭ/математика, индивидуальные курсы и связи, связать все учебные записи и файлы. | Полная сверка количества/сумм/ссылок; нет расширения видимости или потерянных записей. |
| 3. Политики и backend v2 | Добавить проверку пространства/связей, новые use cases, API v2, транзакции, идемпотентность, проверки конфликтов. | Role/resource матрица, конкуренция и e2e проходят на PostgreSQL. Старый API остаётся совместимым до переключения клиента. |
| 4. Клиент | Ввести выбор контекста и кабинеты администратора/курса/ученика; списки, календарь, групповые и индивидуальные потоки. | Полные пользовательские сценарии, адаптивность, доступность и отсутствие утечки данных между контекстами. |
| 5. Пилот и переключение | Пилот на тестовом пространстве, сверка метрик, короткое окно переключения API/клиента и контрольный restore point. | Реальные маршруты и фоновые задачи работают, нет критических ошибок/утечек, владелец продукта принимает выпуск. |
| 6. Сужение схемы | После периода наблюдения удалить старые поля/код и v1 только при отсутствии потребителей; сохранить архивные/экспортные пути. | Зависимости и данные пересверены, миграция необратимой части согласована и задокументирована. |

Вариант по умолчанию — expand/backfill/switch/contract с коротким контролируемым окном записи на этапе переключения. Долгую двойную запись в старую и новую модели **не вводить без отдельного проектирования**: она создаёт расхождения уроков, ДЗ и прав. Если нужен переход без остановки записи, потребуются dual-write, сверка, воспроизводимое восстановление и отдельный план отката; это другой объём работы.

## Правила переноса существующих сущностей

| Текущие данные | Новая запись/проверка |
|---|---|
| `User.role`, `TeacherProfile`, `StudentProfile.teacherId` | Сохранить ID пользователя; создать членство/роль в одном начальном пространстве. На каждую пару преподаватель–ученик создать индивидуальный `Course` с `CourseTeacher` и `Enrollment`. Цель и заметка, относящаяся к преподавателю, переносятся в зачисление; глобальные данные остаются в профиле. |
| Нынешние задания 1–25 и формула | Создать версию программы «ОГЭ / математика / legacy-import» с явным соответствием `taskNumber → taskDefinitionId`. Существующую формулу маркировать как **историческую эвристику**, не как проверенное правило для всех экзаменов. Для новых программ прогноз не показывать без утверждённой формулы. |
| `Lesson` | Сохранить ID и время, привязать к соответствующему курсу, создать снимок ведущего и `LessonParticipant` на старого ученика. Статус и история завершения сохраняются; прошлые занятия не становятся будущими из-за зоны. |
| `Homework` и `HomeworkSubmission` | Привязать к курсу; создать одного `AssignmentRecipient`; сохранить сроки, статусы, все попытки, файлы, комментарии и автора проверки. Не «очищать» доработки. |
| `StudentTaskProgress`, `ProgressHistory` | Перенести к зачислению и ID задания; сохранить исходные события/авторов/время. Если автор или тип события не восстановим, отметить `legacy_unknown`, не придумывать доказательство. Проекции пересчитать и сверить. |
| `MaterialTopic`, `MaterialAttachment`, `FileResource` | Материал остаётся собственностью прежнего преподавателя/пространства и связывается с версией задания; публикация в новом курсе создаётся **только там, где прежний ученик имел доступ**. Сверить каждый ID файла, путь и checksum; не раскрыть библиотеку автоматически всем новым ученикам. |
| `Notification`, токены и сессии | Сохранить допустимые уведомления с конкретным получателем и контекстом; неполные — в отчёт сверки. Нынешние сессии могут потребовать повторный вход при смене модели прав; открытые приглашения проверяются отдельно. |

Миграция использует таблицу соответствий старых и новых ID и повторяемые шаги. Она останавливается при неоднозначной паре преподаватель–ученик, несовпадении версии задания, отсутствующем файле, некорректной дате или ссылке в другом пространстве. Ручное исправление фиксируется в отчёте, а не скрывается значением по умолчанию. Перед удалением старых колонок проводится независимая сверка: число строк по статусам, ссылки, временные интервалы, владельцы файлов, видимость, прогресс и ответы API для выбранной контрольной выборки.

## Проверки по уровням

| Уровень | Обязательные случаи |
|---|---|
| Схема/миграция | Пустая БД, копия старой БД, повторный запуск, частичный сбой, FK/уникальность, отсутствие осиротевших файлов/истории, сравнение старого и нового чтения. |
| Unit/domain | Допустимые/недопустимые переходы, вместимость, время и зона, idempotency, версия программы/задания, расчёт и отсутствие прогноза без правила. |
| Policy | Все роли и составные роли, два пространства, два преподавателя одного ученика, бывший участник, помощник/замена, локальный/глобальный каталог, чужой ID в list/detail/mutation/file. |
| PostgreSQL concurrency | Два зачисления на последнее место; одновременные пересекающиеся уроки для общего ученика и разных преподавателей; двойная публикация ДЗ; конфликт исправления оценки. |
| HTTP/contract | OpenAPI тела/ответы/ошибки, фильтры/пагинация, ETag/If-Match, Idempotency-Key, статус/поле ошибок, старый и новый контракт на период миграции. |
| UI | Админ создаёт группу и зачисляет, преподаватель ведёт группу и персональную консультацию, ученик видит несколько курсов, сдача и проверка не раскрывают однокурсников, массовые действия имеют превью. |
| Эксплуатация | Docker build, миграции, rate limit, фоновые повторы, бэкап/восстановление БД+файлов, остановка/перезапуск, проверка размера диска и журнала ошибок. |

## Сквозные приёмочные сценарии

| ID | Сценарий и ожидаемый результат |
|---|---|
| A01 | Администратор создаёт две программы разных предметов, групповой и индивидуальный курс; одна учётная запись ученика зачислена в оба, без дубля профиля. |
| A02 | Один ученик зачислен к двум преподавателям по одной версии программы; исходные оценки и личные заметки разделены, ученик видит свои опубликованные результаты и происхождение. |
| A03 | Преподаватель ведёт две группы разных предметов; фильтры, материалы, задания и расчёты не смешиваются по совпадающему номеру задания. |
| A04 | Групповой урок приглашает троих, один отсутствует; посещаемость и прогресс каждого индивидуальны. Персональная консультация в том же курсе не затрагивает двоих остальных. |
| A05 | Перенос урока блокируется при пересечении с занятием ученика у другого преподавателя; параллельные запросы не обходят проверку. Администраторское исключение требует причины. |
| A06 | Групповое ДЗ опубликовано для выбранных участников; новый ученик не получает его задним числом, персональный срок и доработка одного ученика не меняют остальных. |
| A07 | Ученик А не может получить ответ, оценку, имя файла или приватную заметку ученика Б через UI, прямой API, старый URL или уведомление. |
| A08 | Выход/перевод из группы не удаляет историю, закрывает новые материалы и корректно обрабатывает будущие уроки и открытые ДЗ с подтверждением. |
| A09 | Замена ведущего не изменяет исторического автора оценок; старый преподаватель теряет новые права, новый видит только допустимый объём. |
| A10 | Новая версия программы не меняет прошлые курсы и оценки. Без подтверждённой формулы нет фиктивного прогноза. |
| A11 | Массовое зачисление при заполнении группы даёт понятный отчёт и не создаёт половину группы без явно выбранной политики. Повтор запроса не дублирует связи. |
| A12 | Восстановленная тестовая БД и файлы согласованы; вход, материалы и сдачи работают после restore. |

## Нагрузочная проверка и выпуск

До утверждения численных SLO сформировать репрезентативный обезличенный набор: несколько пространств, сотни преподавателей, тысячи учеников, тысячи курсов и большой архив уроков, получателей ДЗ и файлов. Измерить p50/p95 списков, календаря, массового набора, сводок и проверок доступа, рост БД/индексов и стабильность под параллельными запросами. Предлагаемые цели и инфраструктуру фиксировать **после** базового замера; документ не выдаёт непроверенную цифру за гарантию.

Перед merge: линт/типизация/сборка, unit, contract, e2e с PostgreSQL, migration check, аудит зависимостей и Docker build зелёные. Перед пилотом: матрица прав, ручная UX-проверка ролей, restore drill и контроль на реальном API. Перед полноценным выпуском: нет критичных утечек/потерь, назначен владелец поддержки, мониторинг и бэкапы активны на фактическом сервере, есть инструкция возврата/исправления и согласована политика хранения.

## Откат и послеаварийное восстановление

До переключения старых клиентов/записи допустим возврат к прежнему коду при сохранённых старых полях. После появления **новых записей** в v2 простое понижение версии приложения или `prisma migrate down` не гарантирует возврата данных. Предпочтителен forward fix на совместимой схеме; восстановление снимка приводит к потере записей после снимка и требует осознанного решения, экспорта/повторного ввода либо периода остановки записи. Развёртывание не начинается без обозначенного rollback point, ответственного и проверки restore на отдельной среде. Старые колонки удаляются только после периода сверки и отдельного подтверждения.

## Поддержание документации

При реализации каждой фазы обновлять статус в [индексе](README.md), фактический [API](../api.md), OpenAPI, миграционные заметки, операционные инструкции и тесты. Проектный маршрут нельзя помечать «реализован» по наличию DTO или UI-макета без e2e с реальной БД и проверкой разрешений. Необратимое решение фиксируется отдельным ADR с альтернативами и причиной.
