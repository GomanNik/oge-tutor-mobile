# Блок 1: запуск и эксплуатация

Этот документ относится только к пространствам, аккаунтам, участникам и приглашениям. Предметы, курсы и группы остаются проектом следующих блоков. API v1 и старые учебные кабинеты продолжают работать. VPS пока нет; локальные проверки не являются подтверждением промышленного развёртывания.

## Перед развёртыванием

1. Проверьте `pnpm run quality`, PostgreSQL e2e, `prisma migrate status` и сборку обоих Docker-образов на том же коммите.
2. На обезличенной копии реальной БД выполните полный backup и restore по [инструкции](../backups.md). Сверьте число `User`, `TeacherProfile`, `StudentProfile`, `Lesson`, `AuthSession`, хеши паролей и контрольные ID до и после миграции. Убедитесь, что у каждого старого преподавателя отдельное пространство, а отключённый ученик имеет `suspended` membership.
3. Приостановите запись на время первого применения миграции, сохраните идентификатор исходного образа и проверенный restore point. Миграция расширяет схему и не удаляет старые таблицы; обратной destructive-миграции нет.
4. Для production настройте независимый `WORKSPACE_INVITE_KEY` длиной от 32 символов, SMTP, URL и прочие обязательные переменные из [env.md](../env.md). Не храните реальные значения в Git, логах или PR.

Промышленный rollout пока **не разрешён**: нет VPS и проверенного восстановления его реальных данных. Слияние PR само по себе не означает включения в production.

## Миграция и сверка

После restore point:

```powershell
pnpm --dir oge-tutor-backend exec prisma migrate deploy
pnpm --dir oge-tutor-backend exec prisma migrate status
pnpm --dir oge-tutor-backend run workspace:operator -- backfill
```

`DATABASE_URL` должен указывать именно на выбранную базу. SQL-миграция сама переносит существующие профили. `backfill` повторяем: он сначала проверяет старые связи и сообщает `ambiguous`/`orphaned` ID, затем добавляет недостающие mapping/membership/grant. Нулевые `workspaces`, `memberships`, `grants` при повторном прогоне ожидаемы. При ошибке не подставляйте фиктивные имена/роли: исправьте исходные данные, повторите проверку и сверку.

Контрольные запросы:

```sql
SELECT count(*) FROM "TeacherProfile";
SELECT count(*) FROM "LegacyWorkspaceMapping";
SELECT count(*) FROM "StudentProfile";
SELECT count(*) FROM "WorkspaceMembership";
SELECT count(*) FROM "WorkspaceRoleGrant";
SELECT count(*) FROM "WorkspaceMembership" WHERE status = 'suspended';
```

Число mapping должно равняться числу старых преподавателей. Membership как минимум равно числу старых преподавателей и их учеников, кроме обнаруженных неоднозначных общих аккаунтов; такие случаи требуют отдельного разбора. Проверяйте связи по ID, не по имени/email.

## Первое пространство

Только на **пустой** БД, после миграции, оператор задаёт неповторяющийся сильный пароль через безопасный ввод. Пример PowerShell:

```powershell
$env:WORKSPACE_ADMIN_EMAIL = 'admin@example.com'
$env:WORKSPACE_ADMIN_NAME = 'Имя администратора'
$env:WORKSPACE_NAME = 'Название пространства'
$env:WORKSPACE_TIMEZONE = 'Asia/Omsk'
$secret = Read-Host 'Пароль первого администратора' -AsSecureString
$env:WORKSPACE_ADMIN_PASSWORD = [System.Net.NetworkCredential]::new('', $secret).Password
try { pnpm --dir oge-tutor-backend run workspace:operator -- bootstrap }
finally { Remove-Item Env:\WORKSPACE_ADMIN_PASSWORD -ErrorAction SilentlyContinue }
```

Повторный `bootstrap` завершается ошибкой и не создаёт второго пользователя/пространства. На БД со старыми кабинетами bootstrap запрещён. Новое пространство для существующего аккаунта создаётся оператором через `WORKSPACE_OPERATOR_USER_ID`, `WORKSPACE_NAME`, `WORKSPACE_TIMEZONE` и `workspace:operator -- create`; публичного API создания пространств нет. Передайте ID аккаунта только из проверенного `/api/v2/me` или БД, не по email-поиску из сообщения.

## Приглашения и почта

Администратор создаёт приглашение с одной или несколькими ролями. Токен живёт 72 часа по умолчанию; повторная отправка ротирует токен, отзыв делает ссылку недействительной. В API/аудит сырой токен не возвращается. В БД остаётся SHA-256 хеш, а ссылка на короткое время хранится в AES-256-GCM outbox до доставки. Раз в 15 секунд worker помечает просроченные приглашения, очищает их недоставленные ссылки, ищет готовые записи, применяет lease и retry с увеличивающейся задержкой до часа. После доставки или отмены зашифрованная ссылка очищается.

Для локальной ручной проверки без внешней почты:

```powershell
docker compose --profile dev-mail up -d mailpit
$env:MAILER_PROVIDER = 'smtp'
$env:SMTP_HOST = '127.0.0.1'
$env:SMTP_PORT = '1027'
$env:SMTP_FROM = 'OGE Tutor <no-reply@localhost>'
```

Запускайте backend в той же оболочке. Письма доступны на `http://localhost:8027`; Mailpit привязан только к loopback и не включается в production-профиль. `MAILER_PROVIDER=noop` пригоден для автоматических тестов, но не позволяет вручную получить ссылку из UI.

Если `deliveryStatus=failed`, проверьте SMTP и оставьте worker повторить отправку. Не копируйте `encryptedLink` в логи. При смене `WORKSPACE_INVITE_KEY` старые недоставленные payload перестанут расшифровываться: сначала дождитесь их отправки либо отзовите приглашения, затем смените ключ. Ротацию ключа и очистку старого секретного значения проводите отдельной операторской процедурой.

## API и права

Swagger: `GET /api/docs`. Вход: `POST /api/v2/auth/login`, выход: `POST /api/v2/auth/logout` (204), профиль и контексты: `/api/v2/me`, `/api/v2/me/workspaces`. Управление: `/api/v2/workspaces/{workspaceId}/members`, `/invitations`, `/audit-events`; принятие: `/api/v2/invitations/accept-new` или `/accept-existing`. Все маршруты пространства требуют Bearer-токен и `X-Active-Role`; роль проверяется по актуальной БД на каждом запросе. Администрирование доступно только активному `admin` своего пространства. Чужая деталь возвращает 404, потеря права — 403.

Для изменения имени, приостановки/возобновления, отзыва роли и resend/revoke приглашения нужен `If-Match: <revision>`; отсутствие — 428, устаревшее значение — 412. Для нового приглашения и назначения роли нужен `Idempotency-Key`; тот же ключ и тело возвращают сохранённый ответ, другое тело — 409. Записи живут не менее 24 часов и затем очищаются worker. Списки используют `limit` (1–100) и непрозрачный `cursor`, а не загружают весь кабинет.

## Мониторинг и откат

Проверяйте `/health/ready`, 4xx/5xx по `requestId`, количество `failed` и старых `queued` outbox-записей, а также время последнего успешного backup/restore. Разбор ошибок не должен печатать пароль, токен, ссылку приглашения или полное письмо в общие логи. При сбое приложения возвращайте предыдущий совместимый образ backend с сохранением расширенной схемы. Не удаляйте новые таблицы. Если уже записаны новые данные, прежде чем восстанавливать снимок, оцените потерю изменений; восстановление сначала проверяется в изолированной среде.
